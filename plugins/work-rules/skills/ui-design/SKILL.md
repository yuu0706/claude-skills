# 画面の設計（UI デザイン）

**読み手は画面を使う人である。** 使う人は、画面を見てから数秒で「何の画面か」と「次に押すもの」を探す。
本 Skill は見た目・構造・配置・状態・CSS の設計を受け持つ。文言は Skill `ui-text` が受け持ち、両者は対になる。

見本の製品は **GitHub の設定画面と Linear** の2つである。規則の解釈に迷ったら、この2つの作りに寄せる。

| 対象 | 既定 | 差分 |
| --- | --- | --- |
| 業務の管理画面・自分用の道具 | **業務画面の密度**（本節以降の基準値） | なし |
| 一般利用者向けの画面 | 業務画面の密度 | **余白と文字を1段広げる**（`<html data-density="comfortable">`） |

## 0. 最初に守る大原則

1. **画面の目的と主要な操作を先に決める。** 見た目は目的に従う。
2. **装飾より密度と整列で整える。** 線・余白・揃えで区切り、色と影で飾らない。
3. **色・余白・寸法はトークンだけを使う。** 直書きしない。既存のテーマ定義があればそれが正本である。
4. **状態の正本は1か所に置く。** 写しを持たない。

## 1. 着手前に決めること

実装に入る前に、次の3行を書いて利用者への報告か作業メモに残す。書けないうちは実装しない。

```text
誰が何をしに来るか: 経理担当者が、承認待ちの申請を確かめて承認する
主要な操作: 承認する（多くても2つ。2つ目は差し戻す）
画面の型: 一覧と詳細
```

- **主要な操作は1つ、多くても2つにする。** 3つ以上が同格に並ぶ画面は、目的が決まっていない。
- **画面の型は「一覧」「詳細」「入力」の3つから選ぶ。** 混ぜる場合は「一覧と詳細」の2列にする（2節）。

## 2. 構造と配置

| 禁止 | 代わりに |
| --- | --- |
| 主要な操作（承認・既読・保存・送信）を本文の末尾に置く | **見出し行の右端か、画面下に固定した操作バーに置く。** スクロール前の最初の画面に必ず見せる |
| 主要な操作を見出し行と末尾の両方に置く | どちらか1か所にする。長い入力・詳細は操作バー、それ以外は見出し行 |
| 削除などの破壊的な操作を主要な操作の隣に置く | 離す。詳細の末尾の「危険な操作」の区画か、「その他」のメニューの中に置く |
| 一覧をカードの格子で並べる | **一覧は表にする。** 行の右端に行ごとの操作を置く |
| 詳細を1列で縦に長く並べる | **詳細は2列にする。** 左に本文、右に属性（担当・状態・日付）。Linear の課題の詳細に寄せる |
| 入力欄を2列・3列に並べる | **入力は1列にする。** ラベルは入力欄の上に置く。GitHub の設定画面に寄せる |
| ナビを上と左と下に分散させる | **ナビは左か上の1か所にする。** 項目が7つを超えたら左に置く（目安） |

- **最初の画面に見せる範囲は、幅 1280×高さ 720 と幅 390×高さ 844 で確かめる。** 前者はノート PC の一般的な表示領域、後者は iPhone の標準の画面に合わせた値である。
- **見出し行と操作バーは `position: sticky` で固定する。** 表の見出し行も同じく固定する。表の見出し行の固定は、表を入れた箱（`components.md` 6節の `.split__list`）に高さがあるときだけ効く。
- **狭い画面（`--bp-md` 未満）の表は、横スクロールの箱（`overflow-x: auto`）に入れ、列を折り返させない。** 列が5つを超えるなら、優先度の低い列を `hidden` ではなく CSS で畳む（`components.md` 4節）。

## 3. 文字だけで機能を説明しない

| 禁止 | 代わりに |
| --- | --- |
| ページの見出しにプロジェクト名・サービス名だけを書く | **見出しには「何の画面か」（対象）を書く。** 例 `申請 #1042`、`メンバー`。サービス名は上部のナビの左端に小さく置く |
| 「この画面では〜できます」の説明文を見出しの下に置く | **機能はアイコンと短いラベルと配置で示す。** 操作できる物は押せる形（ボタン・リンク）にする |
| 状態を文で書く（「この申請はまだ承認されていません」） | **状態は色とバッジで示す。** `承認待ち` のバッジを見出しの横に置く。色だけに頼らず語も入れる |
| 絵文字をアイコンに使う | **線の SVG アイコン（Lucide など）を使う。** 大きさは `--icon-sm`（16px）か `--icon-md`（20px） |
| アイコンだけで意味を伝える | 主要な操作はアイコンとラベルを並べる。アイコンだけのボタンには `aria-label` を付ける |

- **説明文は、操作しても分からない箇所にだけ1行で置く。** 置く場所は対象の直下で、文字は `--color-text-muted` にする。
- 説明文・ラベルの文言そのものは `ui-text` に従う。

## 4. 密度・余白・文字

基準は業務画面の密度である。一般利用者向けは `data-density="comfortable"` で1段広げる。

| 項目 | 業務画面 | 一般利用者向け | 根拠 |
| --- | --- | --- | --- |
| 本文・入力欄・ボタンの文字 | 14px（`--text-md`） | 16px | GitHub の本文が 14px（目安。未実測）。ブラウザの既定が 16px |
| 表のセル・補助の文字 | 13px（`--text-sm`） | 14px | Linear の一覧が 13px 前後（目安。未実測） |
| 見出し | 20px と 16px の2段階まで | 同じ | 3段階以上は差が見分けにくい（目安） |
| 表の行の高さ | 36px（`--row-h`） | 48px | 13px の文字と上下 12px の余白の和（目安）。48px は指で押せる高さ |
| ボタン・入力欄の高さ | 32px（`--control-h-md`） | 40px | GitHub の既定のボタンが 32px（目安。未実測） |
| 余白 | 4px の倍数（`--space-*`） | 同じ | 揃えの基準を1つにする |
| 本文の1行の幅 | 65〜75ch（`--measure` は 70ch） | 同じ | 長文の読みやすさの一般的な目安 |
| 画面の外周の余白 | 左右 24px・上下 16px | 左右 32px・上下 24px | 目安 |

| 禁止 | 代わりに |
| --- | --- |
| 業務画面で本文を 16px 以上・行を 48px 以上にする | 上の表の業務画面の値にする。1画面に表の行が 15 行以上見えるのが目安 |
| 幅 1280 で中央に細い列だけを置き、左右を空ける | 表と2列の詳細は幅いっぱいに使う。文章だけの段落に `--measure` を付ける |
| 見出しを太く大きくして区切る | 区切りは 1px の線（`--color-border`）と余白で付ける |

## 5. AI っぽさの禁止一覧

| 禁止 | 代わりに |
| --- | --- |
| グラデーションの背景・ボタン | 単色の面（`--color-bg` と `--color-bg-subtle`）にする |
| 紫・藍色の既定色 | 主要な操作とリンクは `--color-accent`（青）に固定する。Tailwind の既定の色は消す |
| 意味のない角丸のカードと、その入れ子 | 区画は線と余白で分ける。枠で囲むのは操作の単位がまとまる区画だけにし、入れ子にしない |
| 影の多用 | 影は浮いている面（メニュー・ダイアログ・引き出し）だけに付ける（`--shadow-overlay`・`--shadow-modal`） |
| 絵文字のアイコン | 線の SVG アイコンにする（3節） |
| ヒーロー画像・装飾の図形・大きな見出しの導入部 | 最初の画面に、データと主要な操作を置く |
| Lorem ipsum・意味のない仮の値 | 実際の業務に近い値（`山田太郎`・`出張旅費の精算`）を入れる |
| 使わない機能のボタン・作りかけの導線 | 置かない。必要になった時点で足す |
| 読み込み時の飾りの動き・跳ねる動き | 動きは開閉と状態の変化だけにし、`--duration-*` の範囲に収める |
| 中央寄せの説明文 | 左寄せにする。中央寄せは空状態の短い文だけにする |
| 数字を大きく並べた飾りの集計欄 | 業務の判断に使う数だけを、表の上に1行で並べる |

## 6. トークンと部品

**画面を作る前に、`references/` を必ず読む。**

| ファイル | 中身 |
| --- | --- |
| `references/tokens.css` | 素の CSS 変数。色・余白・文字・角丸・影・重なり順・画面幅の境目。ライトとダーク |
| `references/tokens-tailwind.css` | 同じ値の Tailwind v4 の `@theme` 版 |
| `references/components.md` | 部品の雛形。見出し行、操作バー、ボタン3種、表、フォーム、一覧と詳細、空・読込・エラー、引き出し |
| `references/checklist.md` | 提出前の点検 |

| 禁止 | 代わりに |
| --- | --- |
| 色・余白・文字サイズ・角丸・影・z-index を直書きする | トークンの変数だけを使う。足りない値は tokens に名前を付けて足してから使う |
| 既存のテーマ定義があるプロジェクトに本 Skill のトークンを持ち込む | **既存のテーマ定義を正本にする。** 本 Skill からは構造と配置の規則だけを使う |
| 見た目を整えるために新しい UI ライブラリを足す | 既存のライブラリと既存の部品で作る |

既存のテーマ定義の例は次のとおりである。

| 使っている仕組み | 正本 |
| --- | --- |
| MUI | MUI のテーマ（`createTheme` の定義ファイル） |
| Tailwind v4 | `@theme`（グローバルの CSS） |
| 素の CSS | CSS 変数（`:root`） |

本 Skill のトークンを使うのは、新規のプロジェクトと、テーマ定義が無いプロジェクトだけである。
ダークは `prefers-color-scheme` に従い、利用者が選んだときは `<html data-theme="dark">` で上書きする。

## 7. 状態

**空・読込・エラー・無効・成功の5状態を、最初の実装から用意する。** 後から足すと配置が崩れる。

| 状態 | 禁止 | 代わりに |
| --- | --- | --- |
| 空 | 「データがありません」だけを出す | 次の操作のボタンかリンクを1つ置く。文言は `ui-text` |
| 読込 | 画面全体を回転アイコンで覆う | データが出る場所に行の形の骨組みを出す。見出し行と操作は残す |
| エラー | 画面全体をエラーページに差し替える | データが出る場所に、何が起きたかと再試行のボタンを出す。入力済みの内容を残す |
| 無効 | 押せないボタンを隠す・理由を示さない | `disabled` で灰色にし、押せない理由を近くに1行で示す |
| 成功 | 画面を遷移させて完了を伝える | 操作した場所の近くに短い通知を出し、数秒で消す |

## 8. 拡張性（再発を防ぐ設計）

根拠は、Markdown の閲覧用の Web アプリでの再発の分析である（2026-10-15、git の履歴の観測）。UI を直すたびに前に直した不具合が戻った。原因を型 A〜F に分けた。

| 型 | 起きたこと（観測） | 禁止 | 代わりに |
| --- | --- | --- | --- |
| A 1つの変数を意味の違う読み手が共有 | 幅の上限の変数を、JS が「控えに書く上限」としても読み、利用者の控えを潰した。4回直した | 1つの変数・定数に複数の意味を持たせる。描画後の実測値を控えに書く | **1つの名前に意味は1つ。** 「表示の上限」「利用者の控え」「実測値」を別の名前にする。控えには利用者の操作の値だけを書く |
| B 状態の写しを別の場所に持つ | 下段が左メニューの位置を写して持ち、引き出しが開いた状態を知らずに被った。面を足したときに同じ不具合を入れた | 機能ごとに「他の機能が開いたら」を個別に実装する | **開閉の状態（メニュー・引き出し・面・下段）を `<html>` の data 属性の1か所に集める。** 各機能はそれを読むか購読する（`components.md` の0節） |
| C 機能ごとの CSS が互いを知らない | JS の `hidden` を `display:flex` が打ち消した。詳細度で負けて右列が残った。z-index を 7 と 5 で別々に決めて衝突した | 詳細度を上げて勝ちにいく。`!important` を書く。z-index に生の数値を書く | **z-index は層の変数（base・sticky・drawer・overlay・modal・toast）だけを使う。** 勝ち負けは `@layer` か読み込み順で明示する。表示の切り替えは `hidden` ではなく data 属性と CSS で行う |
| D ライブラリの内部の指定に依存 | Material の `padding-right` と `font-size:125%` を見ずに幅を机上で換算した。隙間を 0 で打ち消して既定の余白まで消した | 机上の換算で寸法を決める。0 で打ち消す | **上書き先の既定値とその理由をコメントに書く。** 打ち消すときは既定の値に戻す。寸法はブラウザで実測して決める |
| E ある修正が別の前提を外す | `overflow` を `visible` にしたら、`hidden` が切り取っていたはみ出しが現れた。落ちた検査の範囲を絞って通した | 落ちた検査の範囲を絞って通す | **既存の指定を変える前に、その指定が支えていた副作用を確かめる。** 検査が落ちたら検査の意図に照らして直す。指定を残す理由（Why not）をコメントに書く |
| F 境界値と換算の直書き | 画面幅の境目 60em が JS の5か所と CSS に直書きされていた。1rem を 16px と誤って換算した | 境目と換算の値を複数の場所に書く | **画面幅の境目は tokens の `--bp-*` に1か所で定義する。** JS は `matchMedia` の共通関数から読む。CSS の `@media` には値を書き、変数名をコメントで添える |

- **新しい面・列・引き出しを足す設計では、次の3つを必ず論点に入れる。** 上の分析の対象の設計資料にはこれらが無く、実装中に決めていった。
  1. 他の開閉状態との組み合わせ（すべての組み合わせで何が見え、何が隠れるか）
  2. 重なり順（どの層に置くか）
  3. 狭い画面（`--bp-md` 未満で畳むか、引き出しにするか）
- 設計を資料に書くときは Skill `doc-writing` に従う。

## 9. 提出前の点検

1. **`references/checklist.md` の全項目に「はい／いいえ」で答える。** 「いいえ」は直すか、直さない理由を報告に書く。
2. **Skill `chrome-check`（導入されている場合）など、ブラウザを操る道具でスクリーンショットを撮る。**
   - 幅 1280 と 390 の2枚を撮る。
   - 開閉状態（メニュー・引き出し・面）の組み合わせごとに撮る。開閉が2種類あれば 2×2=4 通りを、2つの幅で撮る。
   - ライトとダークの両方を撮る。OS のダーク設定を模擬できない道具（2026-10-15 時点の `chrome-check` など）では、ダークは `<html data-theme="dark">` を付けて撮る。
   - JS の例外と `console.error` が0件であることを確かめる。
3. **撮った画像を自分で見て、主要な操作がスクロール前に見えることを確かめる。** 見ていない画像を根拠に「確認済み」と書かない。
