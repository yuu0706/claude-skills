# 画面文言（UIテキスト）の書き方

**読み手は開発者ではなく、サービスを使うエンドユーザーである。**
資料（`doc-writing`）は正確さと追跡可能性を優先するが、UI文言は
**その場で迷わず次の操作ができること**を最優先にする。したがって文体規則が異なる。

メールの担当は送り手で分ける（2026-10-02 決定）。サービスが利用者へ自動で送るメール（登録完了・申込受付等）は本 Skill、業務の連絡として人が送るメールは `doc-writing` が担当する。

| | 業務資料（`doc-writing`） | 画面文言（本 Skill） |
| --- | --- | --- |
| 文体 | 常体（である） | **敬体（です・ます）** |
| 長さ | 一文100文字まで | **できるだけ短く。1文20〜40文字を目安** |
| 主体 | システム・担当者を明示 | **ユーザーの行動を主語にする** |
| 目的 | 判断の根拠を残す | **次の操作を迷わせない** |

## 0. 最初に守る大原則

1. **会話の口調・キャラクター名・内輪ネタを画面に出さない。** 画面文言は製品の一部であり、
   社外のエンドユーザーが読む。リポジトリに残るものに口調を持ち込まない原則が、より強く適用される。
2. **プログラム目線で書かない。** 「データがありません」「処理に失敗しました」は内部の都合。
   ユーザーが**何をすればよいか**に翻訳する。
3. **ユーザーを責めない。** 「間違っています」「不正な値です」「無効」は使わない。
4. **迷ったら判断基準は1つ。** 「この画面を初めて見た人が、次に何をすればよいか分かるか」。

## 1. 文体

- **敬体（です・ます）で統一する。** 常体・体言止めと混在させない。
- **敬語は「です・ます」で止める。** 過剰な敬語は読みにくく、かえって不親切。
  - ✕ 「ご入力いただけますでしょうか」／○ 「入力してください」
  - ✕ 「送信させていただきました」／○ 「送信しました」
- **命令形は使わず「〜してください」にする。** ただしボタンラベルは別（後述）。
- **「あなた」を多用しない。** 日本語では主語を省いても通じる。
  必要な場合だけ「お客様」を使い、1画面内で呼び方を変えない。
- **句点（。）の付け方を要素ごとに統一する。**
  - 文の形をしているもの（説明文・エラーメッセージ・ヘルプ）は句点を付ける。
  - 語句・単語のもの（見出し・ラベル・ボタン・プレースホルダー）は**句点を付けない**。
- **感嘆符（！）を使わない。** 「完了しました！」の勢いは不要。
- **専門用語・社内用語をそのまま出さない。** ユーザーが普段使う言葉に置き換える。
  - ✕ 「トークンが失効しました」／○ 「ログインの有効期限が切れました」
  - ✕ 「バリデーションエラー」／○ 「入力内容を確認してください」
- **表記（長音・全角半角・数字・ひらがな漢字の使い分け）は JTF 日本語標準スタイルガイドに従う。**

## 2. ボタンとリンク

- **ボタンラベルは、押した結果が分かる動詞にする。** 汎用語で済ませない。
  - ✕ `OK` `はい` `送信` `実行`／○ `申し込む` `保存する` `削除する` `メールを送信`
  - 特に**確認ダイアログの「はい／いいえ」は禁止。** 動作名を入れる（→ 4）。
- **同じ操作を、画面によって別の語で呼ばない。** 用語を1つに決める。
  - `キャンセル` と `取り消す` を混在させない／`削除` と `除去` を混在させない
  - `保存` と `登録` は意味が違う。新規作成は `登録`、既存の更新は `保存` に固定する
- **ラベルは短く。目安は全角2〜8文字。** 説明が必要ならボタンの外に補助テキストを置く。
- **リンクテキストは、遷移先が分かる語にする。** 「こちら」「詳細」「ここをクリック」を使わない。
  - ✕ 「詳しくは[こちら](#)」／○ 「[チケットの受け取り方](#)を確認する」
  - 理由: スクリーンリーダーはリンクだけを読み上げる。文脈が切れると意味が通らない。
- **破壊的な操作のボタンは、動作名を明示して色だけに頼らない。**
  赤いだけの `OK` ではなく `アカウントを削除する` と書く。

## 3. フォーム

- **ラベルは必ず表示する。** プレースホルダーをラベルの代わりにしない。
  入力を始めると消えるため、何の欄か分からなくなる。
- **プレースホルダーは入力例だけを入れる。** 説明や必須の指示を入れない。
  - ○ `例）yamada@example.com` `例）2026-08-26`
  - ✕ `メールアドレスを入力してください`（← ラベルに書くべき内容）
- **入力の制約は、入力前に示す。** エラーで初めて知らせるのは遅い。
  - ○ ラベル下の補助テキストに「半角英数字8文字以上」
- **必須・任意は文字で示す。** 色や `*` だけに依存させない。
  - ○ `メールアドレス（必須）`
  - 任意項目が少数なら「（任意）」を付ける方式にし、画面内で方式を混在させない。
- **入力形式を人間の言葉で書く。** 「YYYY-MM-DD形式」より「例）2026-08-26」。

## 4. 確認ダイアログ

**目的は「取り消せない操作を、意図して行ったか確かめること」。** 不可逆かどうかを必ず書く。

構成は次の3つ。

1. **タイトル**: 何をしようとしているか。短く。句点なし。
   - ○ `このチケットを削除しますか`
2. **本文**: 実行すると何が起きるか。**元に戻せない場合はそれを明記する。**
   - ○ `削除すると元に戻せません。関連する申込履歴も削除されます。`
3. **ボタン**: 動作名を入れる。**危険な側を既定の選択にしない。**
   - ○ `削除する` / `キャンセル`
   - ✕ `はい` / `いいえ`

- **確認ダイアログを、取り消せる操作に出さない。** 毎回出る確認は読まれなくなる。
- **件数や対象名を本文に埋め込む。** 「3件の申込を削除します」のように、対象を取り違えられない形にする。

## 5. エラーメッセージ

**文型は「何が起きたか」＋「どうすればよいか」。** どちらか一方だけにしない。

| ✕ 使わない | 理由 | ○ 代わりに |
| --- | --- | --- |
| `電話番号が間違っています` | ユーザーを責めている | `電話番号は半角数字で入力してください` |
| `失敗しました` | 次の行動が分からない | `保存できませんでした。時間をおいてもう一度お試しください` |
| `画像データがありません` | プログラム目線 | `画像を選択してください` |
| `不正な値です` `無効です` | 責めている・意味が伝わらない | 何をどう直せばよいかを書く |
| `カタカナで入力` | 文になっていない | `カタカナで入力してください` |
| `エラーが発生しました` のみ | 何も伝えていない | 原因の分類と次の操作を書く |
| `Internal Server Error` `404` のみ | 専門用語・エラーコードが主役になっている | 本文は日本語で書き、コードは補助として小さく併記する |

- **ユーザーに直せることは、直し方を書く。** 直せないこと（サーバー側の障害）は、
  **ユーザーの責任ではないと分かる書き方にし、次の行動（再試行・問い合わせ）を示す。**
  - ○ 「一時的に処理できませんでした。数分後にもう一度お試しください。」
  - ○ 「ログインの有効期限が切れました。お手数ですが、もう一度ログインしてください。」
- **入力済みの内容を消さない。** 再入力を強いるエラー画面を作らない。
- **表示場所を使い分ける。**
  - **インライン**（該当項目の直下）: 入力値の誤り。最もストレスが少ない。原則こちらを使う。
  - **ページ上部またはボタン付近**: 複数項目にまたがる誤り。どの項目かをリンクで示す。
  - **モーダル**: 操作を中断させる必要があるとき。タイトルに次のアクションを書く。
  - **別ページ**: 通信不能・権限なし・存在しないページ。戻り先の導線を必ず置く。
- **エラーコードは、問い合わせに使う場合だけ併記する。** 主役にしない。
  - ○ 「保存できませんでした。時間をおいてもう一度お試しください。（コード: E-1042）」
- **色・アイコンだけでエラーを表さない。** 必ず文字でも伝える（グレースケールでも通じるか確認する）。
- **ユーモアを入れない。** 困っている人には響かない。

## 6. その他の状態

- **空状態（データが0件）**: 「データがありません」で終わらせない。**次の一手を書く。**
  - ○ 「まだ申込がありません。イベントを選んで申し込んでください。」
- **処理中**: 何を待っているかを書く。長い処理は目安を添える。
  - ○ 「アップロードしています…（最大1分ほどかかります）」
- **完了**: 何が起きたかを過去形で簡潔に。感嘆符は不要。
  - ○ 「保存しました」「申込を受け付けました」
- **権限がない**: 「権限がありません」だけで終わらせず、誰に依頼すればよいかを書く。

## 7. HTML 固有の文言

コードに書く文字列のうち、**画面に出ないが読み上げ・検索・タブに出るもの**を落としやすい。

- **`<html lang="ja">` を必ず指定する。** 音声読み上げの言語エンジンが切り替わる。
  一部だけ別言語のときは、その要素に `lang` を付ける。
- **`<title>` はページ内容が分かる日本語にする。** タブ・履歴・検索結果に出る。
  - ✕ `404 not found`／○ `ページが見つかりません | サンプルサービス`
  - 「ページ名 | サイト名」の順にする（先頭が切られても識別できる）。
- **`alt` は画像の役割で書き分ける。**
  - 情報を持つ画像: 何が写っているか・何を伝えているかを書く
  - 装飾画像: `alt=""` にする（読み上げから除外する。省略ではなく空文字を書く）
  - 画像リンク: 画像の説明ではなく**遷移先**を書く
  - 文字画像: 画像内の文字をそのまま書く
- **アイコンだけのボタンには `aria-label` を付ける。** ○ `aria-label="メニューを開く"`
- **`<label>` を入力欄に紐づける**（`for` と `id`）。見た目だけラベルらしい `<div>` にしない。
- **見出しは `h1` から順に、階層を飛ばさずに使う。** 文字サイズのために見出しタグを選ばない。
  見出しのテキストは、その節の内容を表す語にする。
- **位置・形・色に依存する説明を書かない。**
  - ✕ 「右のボタンを押してください」「赤い項目は必須です」
  - ○ 「［申し込む］ボタンを押してください」「（必須）と書かれた項目は入力が必要です」
- **`placeholder` は装飾ではなく入力例。** `title` 属性で説明を代替しない（多くの環境で読めない）。
- **`<button>` と `<a>` を使い分ける。** 操作は `button`、遷移は `a`。文言も「〜する」と「〜へ」で対応させる。

## 8. 実装上の注意

- **文言をテンプレートに直書きして散らさない。** 同じ意味の文言が複数箇所に散ると、
  必ず表記がずれる。定数・辞書・i18n ファイルに集約する。
- **文言を変えたら、テストコード・スナップショット・E2E のセレクタも合わせて直す。**
- **サンプルやモックの固定値に作品名・キャラクター名を使わない**（`山田太郎` `test_user_01` などを使う）。
- **文言だけを変える変更は、その旨をコミットメッセージに書く。** レビュアーが挙動変更と区別できる。

## 9. 提出前チェック

- [ ] 敬体（です・ます）で統一されているか。常体・体言止めと混ざっていないか
- [ ] 会話の口調・キャラクター名・感嘆符が残っていないか
- [ ] ボタンが `OK` `はい` `送信` のような汎用語で終わっていないか
- [ ] 同じ操作を画面によって別の語で呼んでいないか（キャンセル/取り消す、保存/登録）
- [ ] リンクテキストが「こちら」「詳細」になっていないか
- [ ] エラーメッセージに「どうすればよいか」が書かれているか
- [ ] エラーメッセージがユーザーを責めていないか（間違っています／不正／無効）
- [ ] 専門用語・内部用語がそのまま出ていないか（トークン、バリデーション、レコード）
- [ ] 不可逆な操作の確認ダイアログに「元に戻せない」と書かれているか
- [ ] 空状態に次の一手が書かれているか
- [ ] 色・位置・形だけに依存した説明になっていないか
- [ ] `lang` `title` `alt` `label` `aria-label` が埋まっているか（装飾画像は `alt=""`）
- [ ] 見出しの階層が飛んでいないか
- [ ] 表記が JTF 日本語標準スタイルガイドに従っているか（長音・全角半角の間のスペース・記号）
- [ ] 文言が1箇所に集約されているか（同じ文言の重複定義がないか）
