# サブエージェントの運用

本 Skill は、サブエージェント（メインの Claude から作業を任される別の Claude）の起動・監視・評価と、作業の分け方の規則である。

## 0. 上書きファイル

利用者ごとの起動の運用（別アカウントで起動するラッパー、アカウントごとの設定ディレクトリ、ステータスバーへの表示など）は本文に書かず、上書きファイル `~/.config/claude-skills/sub-agent-ops.local.md` に書く。

- サブを起動する前に、このファイルがあれば読んで従う。本文と食い違う箇所は、上書きファイルを優先する。
- ファイルが無ければ、「1」の既定（`Agent` ツール）で起動する。別アカウントのラッパーで起動する運用をしているかを利用者に聞き、している場合は聞いた内容（起動のコマンド、使うモデルと effort、進捗ファイルの置き場所の制約）でファイルを作る。

## 1. 起動の方法

- **既定は `Agent` ツールで起動する。** 作業中に方針変更や差し戻しを流せるためである。
- **別アカウントのラッパー（`claude -p` を包んだスクリプトなど）で起動する運用をしている場合は、上書きファイルに従う。** 利用枠を分ける目的で、メインと別のアカウントでサブを動かす運用が当たる。
- 非対話の `claude -p` で起動する場合は、モデルと effort を必ず明示する（`--model`・`--effort`）。アカウントによって既定のモデルが違い、利用枠やクレジットの都合で即座に終わることがある。
- 非対話で起動したサブは、バックグラウンドで動かし、進捗ファイルで監視する（「4」）。

## 2. モデルと effort

- **サブにも、検証の設計まで任せられる性能のモデルを使う。** 軽いモデルは実装そのものは通しても、検証の設計が甘くなりやすい。通ったという報告を信用して統合すると、稼働中の環境を止めることがある。
- **effort は消費とのつり合いで決める。** 高い effort のサブを複数台動かすと、利用枠の消費が大きくなる。まず低めにし、速度や品質に不満が出たら上げる。
- 利用者ごとの具体的なモデルと effort の値は、上書きファイルに書く。

### `Agent` ツールで動かすサブ

- モデルと effort は、エージェント定義（`.claude/agents/*.md`）の frontmatter に書く。
- `Agent` ツールの `model` パラメータでは上書きしない。定義と食い違い、どちらが効いているか分からなくなる。
- 定義はユーザー単位（`~/.claude/agents/`）またはリポジトリ単位（`<リポジトリ>/.claude/agents/`）に置く。定義の無い場所では、この規則は効かない。

## 3. 使う条件

- **複数のタスクを同時に進められる場合にのみ使う。** 単一の調査には使わない。
  例外として、Skill `grilling` で質問を進める間の事実の調査は1件でも任せてよい。
- ファイルと箇所が既に分かっている確認には使わない。自分で読む。
- 独立した作業は1回のメッセージにまとめて並列で投げる。投げたあとに同じ調査を自分でも走らせない。
- 結果が返る前に、返ってきたことにして話を進めない。

### 3.1 調べる前にナレッジを引く（2026-10-06 追加）

プロジェクトのナレッジ検索の道具（会話の開始時に案内が出るもの）がある場合は、次の手順を守る。具体的な使い方は上書きファイルに書く。

- **メイン自身も、判断と調査の前に引く。** 対象の用語で検索し、0件なら語を変えて2〜3回（別の用語・英語と日本語・略語・関連する症状）試す。それでも0件なら知識なしとして扱い、推測で埋めない。ヒットは要約なので、使う前に全文を読む。
- **サブに調査を任せる依頼文には、この手順をそのまま書き込む。**「調べる前にナレッジを引く。語を変えて2〜3回試す。ヒットは全文を読む。0件なら推測しない。新しく分かったことは結論を1行の題にして登録し、誤りを見つけたら訂正を付ける」の5点を、道具の具体的な使い方と併せて書く。本 Skill を読んでいないサブは、この手順を知らない。
- 引いた知識は、「6.2」の共有調査の結果と同じく、具体的な値として依頼文に埋め込む。

## 4. 進捗ファイルによる監視

サブはバックグラウンドで起動し、最終報告だけを待たずに途中も確認する。

- エージェントごとに進捗ファイルを1つ指定する（例: `~/.local/state/agent-reports/progress-<ラベル>.md`）。
  並列時は書き込みが衝突するため必ず分ける。
- **非対話で起動するサブには、進捗ファイルと最終報告のファイルを `~` の下に置かせる。** サブの作業場所の外（一時ディレクトリなど）は、書き込みが黙って拒否されることがある。
- **非対話で起動するサブには、最終報告を標準出力ではなくファイルに書かせる。** `-p` の標準出力は最後の応答だけで、hook への返事に置き換わることがある。
- プロンプトに次を必ず含める ── 節目ごとに**追記**（上書きしない）。1件につき
  「時刻 / 何を調べたか / **根拠となるファイルパスと行番号** / 次にやること / 詰まっている点」。
  根拠が見つからなかった場合も、探索を打ち切る場合も、その旨と理由を書く。
- 待っている間に読み、**根拠の無い主張が積まれていないか**、更新が止まっていないか、
  指示した範囲から外れていないかを確認する。止まっていれば中断とみなす。

## 5. 報告の扱い

- サブの報告はユーザーには見えない。必要な部分は自分の言葉で要約して伝える。
- 結論をそのまま採用しない。**進捗ファイルと最終報告が食い違う場合は自分で確かめる。**
- 本番環境に触る作業はサブに任せない。メインが自分で実行し、自分で確認を取る。

## 6. 作業の分け方

2026-10-06 に Skill `agent-pipeline` から移設した。
作業を複数の役割（リーダー・設計・実装など）に分けて任せる前に、本節で分け方を決める。
役割を分けて並列に投げるだけでは、各役割が同じ背景を別々に調べ直し、依存のある工程まで同時に走る。その結果、利用枠の無駄遣い・手戻り・往復の質問が起きる。

### 6.1 最初に確かめる判断基準

下流の役割（例: 実装）が、上流の役割（例: 設計）の何を必要とするかで分ける。

- **成果物（決定・ファイル・仕様）だけで足りる。** 独立した作業であり、並列でよい。
- **判断の過程・理由・却下した選択肢まで必要である。** 依存した作業であり、並列にしない。

上流の役割が質問を返してくる、または指示に無いことを自分で決めているなら、その役割は清書役ではなく意思決定者である。その結論が確定するまで、下流に着手させない。

### 6.2 共有調査を1回だけ先に行う

各役割に資料を調べさせる前に、メインが現状のファイルパス・行番号・制約・既存の決定事項を一度だけ調べる。既存の決定事項は、まず「3.1」のとおりナレッジから引く。
調べた事実は、各役割への指示に具体的な値として埋め込む。「調べて」ではなく「〇〇は `file:line` でこうなっている」まで書く。同じ調べ物を複数の役割に繰り返させない。

### 6.3 依存関係で実行順序を決める

下流が上流の判断に依存するなら、順番に実行する（設計の決定が確定してから実装に着手する）。
並列にするのは依存の無い作業だけである（「3」の「独立した作業は1回のメッセージにまとめて並列で投げる」）。役割を分けたことと、並列に走らせてよいことは別である。

### 6.4 任せる先の選び方

起動の方法・モデルと effort・監視は「1」〜「4」に従う。本節は、どの種類のエージェントに任せるかだけを扱う。

- **直前までの会話と調査結果をそのまま引き継がせたい。** 文脈を丸ごと引き継ぐ仕組み（`Agent` ツールの fork など）を使う。資料の調べ直しが起きない。
- **独立した作業で、必要な情報を指示文に書き切れる。** 新しいエージェントを使う。事前の知識が無い前提で、事実・ファイルパス・決定事項を埋め込んだ自己完結した指示文を書く。
- **規模が大きく、順序・並列・出力の形式を厳密に制御したい。** 多段の制御の仕組み（ワークフローなど）を使う。上流の出力は構造化（スキーマで強制）し、上流が1件終わるごとに下流がその1件に着手する形にする（全体の待ち合わせを作らない）。

### 6.5 清書役を疑う

ある役割が独自の判断を一切していない（指示の言い換えと清書だけをしている）なら、その役割を無くして上流にまとめる。中継を増やすほど、伝達と調べ直しの手間が積み重なる。

### 6.6 避けるべき分け方

- 曖昧な方針だけを複数の役割へ同時に配り、各自に背景を調べさせる（調査の二重払い）。
- 下流が上流の判断に依存するのに、両者を並列で走らせる（手戻りと前提のずれの原因になる）。
- 質問を返してくる役割を、清書役のまま扱い続ける（実際には意思決定者である）。
- 引き継ぎのたびに、生の会話ログをそのまま渡す。要点が構造化されず、暗黙の判断の根拠が抜ける。渡すなら「決定事項・理由・却下した案・残課題」に整理してから渡す。
