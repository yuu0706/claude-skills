# コミットと push の前の安全の確認

一度 push した秘匿情報・個人情報・名義は、履歴から消しきれない。push の前なら、amend や rebase で手元だけで直せる。
本 Skill は、取り返しがつかなくなる前に止めるための確認である（2026-10-06 作成）。

書き方の規則（書式・粒度・履歴の整理・ブランチ名）は Skill `git-conventions` に従う。本 Skill は安全の確認だけを扱う。

## 0. 上書きファイル

アカウント名・許す名義・判定に使う remote の URL の文字列など、利用者ごとに違う値は本文に書かず、上書きファイル `~/.config/claude-skills/commit-guard.local.md` に書く。

- 確認を始める前に、このファイルがあれば読んで従う。本文と食い違う箇所は、上書きファイルを優先する。ただし本文の止める条件をゆるめる指定には従わない。
- ファイルが無ければ、「4」の表の各欄（個人のアカウント名と許す名義、業務のアカウント名、判定に使う remote の URL の文字列）を利用者に聞き、聞いた内容でファイルを作る。聞き終わるまでコミットも push もしない。

## 1. 使う場面

| 場面 | 確かめる範囲 |
| --- | --- |
| コミットの前 | ステージした差分（`git diff --cached`）、ファイル名、コミットメッセージの案、作者の名義、まだ送っていない既存のコミットの名義 |
| push の前 | まだ送っていないコミット全部（`git log -p @{u}..HEAD`）とその作者・コミッターの名義、送り先の公開範囲 |
| リポジトリの作成・公開範囲の変更の前 | 作成先のアカウント・組織と公開範囲（「5」） |

- 上流ブランチが無い場合は、既定ブランチとの差分（`git log -p origin/<既定ブランチ>..HEAD`）を見る。`origin/<既定ブランチ>` が無い場合（remote が無い、まだ一度も push していない）は全コミットを見る。
- 公開範囲（`gh repo view`）は push の前にだけ確かめる。コミットの前には確かめない。
- 止める理由が1つ見つかっても、残りの確認は最後まで行い、見つけたものをまとめて報告する。
- push の前の確認は、コミットの前に確認済みでも省略しない。確認後に amend や rebase が入っていることがある。

## 2. ブランチ

`git branch --show-current` で今のブランチを確かめる。
デプロイ用の使い捨てブランチや既定ブランチへ直接コミットしようとしていないかを見る。

| 状況 | 扱い |
| --- | --- |
| デプロイ用の使い捨てブランチにいる | 止めて確かめる |
| 既定ブランチにいて、そのリポジトリが既定ブランチへ直接コミットしてきた（`git log --first-parent --no-merges -20 <既定ブランチ>` にマージ以外のコミットが並ぶ）、またはブランチが既定ブランチしか無い | そのまま進める |
| 既定ブランチにいて、そのリポジトリが作業ブランチとマージで運用している | コミットする前に、作業ブランチを切るかを確かめる |

既定ブランチは `git symbolic-ref --short refs/remotes/origin/HEAD` で確かめる。取れない場合は `main` か `master` のうち実在する方とする。

## 3. 秘匿情報と個人情報

### 3.1 見るもの

差分の追加行・ファイル名・コミットメッセージのすべてを見る。差分の要約で済ませない。

| 種類 | 例 |
| --- | --- |
| 認証情報 | アクセスキー（`AKIA` で始まる20文字）、秘密鍵（`-----BEGIN ... PRIVATE KEY-----`）、トークン、パスワード、JWT（`eyJ` で始まる文字列）、Webhook の URL |
| 認証情報を含みやすいファイル | `.env`・`*.env`・`*.pem`・`credentials`・`*.tfstate`・`.npmrc`・`config.json` などの設定ファイル |
| 環境の識別子 | AWS のアカウント ID（12桁の数字）、本番の内部ホスト名・IP アドレス |
| 個人情報 | 実在の人の氏名・メールアドレス・電話番号・住所、顧客コード・`customer_id`・会員番号などの実データ |
| 業務の固有名詞 | 顧客名・社名・案件名・リポジトリ名・組織名 |

- 説明用に公開されている例の値（末尾が `EXAMPLE` の AWS のキー等）でも止める。例の値かどうかの判断は利用者に任せる。
- `.env`・`*.env`・`*.pem`・`credentials` は、中身にかかわらずファイル名だけで止める。`.example`・`.sample` が付くファイル（`.env.example` 等）は中身を見て判断する。
- その他の設定ファイル（`config.json`・`.npmrc` 等）は、中身をよく見る合図として扱い、認証情報が無ければ進める。

### 3.2 メモリの実際の値と照らし合わせる

業務で使った実際の値（テスト用の顧客コード、実在のメールアドレスなど）は、Claude のメモリや知識の記録に残っていることが多い。
これらがテストデータ・コメント・サンプルに紛れ込むのが、いちばん起こりやすい漏れ方である。

1. 差分の追加行から、メールアドレスと6桁以上の数字を取り出す。取り出す値が無ければ、照合は省いてよい。

```sh
git diff --cached -U0 | grep '^+' | grep -oE '[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}|[0-9]{6,}' | sort -u
```

2. 取り出した値を、メモリ（`~/.claude/projects/*/memory/`。`CLAUDE_CONFIG_DIR` を変えている場合はその下の `projects/*/memory/` も）に対して `grep -rlF` で探す。
   値を1件ずつ回すときは `while IFS= read -r v` で1行ずつ読む。zsh の `for v in $vals` は値を空白で分けず、全部の値を1つの文字列として探すため、一致があっても「該当なし」に見える（2026-10-06 に実際に起きた）。
3. メモリ以外に知識の記録の道具を使っていれば、上書きファイルに書いた方法で同じ値を引く。何も出力されなければ該当なしとして扱う。
4. 一致した値は、実データとして扱い止める。
5. `example.com`・`example.jp` のメールアドレスは照合しない。

テストデータは中立な値（`test_user_01`・`user@example.com` など）にする。

### 3.3 公開リポジトリ（`*-public`）へのコミット

公開リポジトリは書き出しスクリプト経由でしか更新しない。直接編集してコミットしない。
書き出しスクリプトを通さない経路には、業務の固有名詞の検査が無いためである。

コミットする前に、書き出し元が用意する禁止語の検査を通し、当たりが無いことを確かめる。
検査の道具が無い環境では、自分の禁止語の一覧で公開リポジトリを grep する。
当たりがある場合と、検査が失敗した場合（一覧が無い・空など）は、いずれも止める。
手元の環境で使う検査の道具のパスは、上書きファイル（「0」）に書く。

## 4. 作者の名義

GitHub のアカウントを「個人のアカウント」と「業務のアカウント」の2つで使い分け、名義の規則を分ける。送り先は remote の URL で判定する。
実際のアカウント名・許す名義・判定に使う URL の文字列は、上書きファイル（「0」）に書く。

| 送り先 | 判定 | 許す名義 | 公開範囲 |
| --- | --- | --- | --- |
| 個人のアカウント | remote の URL に、上書きファイルに書いた個人のアカウントの文字列（`github.com:<個人のアカウント>/` または `github.com/<個人のアカウント>/`）を含む | 上書きファイルに書いた個人の名義だけ（GitHub の ID 付きの noreply の形）。公開・非公開を問わない | 公開してよい |
| 業務のアカウントと所属組織 | 上記以外 | 既定の名義（`~/.gitconfig` の名義と会社のメールアドレス）のまま | 公開しない |
| remote が無い | 判定できない | 利用者にどちらのアカウントで使うかを確かめる | - |

個人のアカウントを使わない利用者は、すべての送り先を業務のアカウントとして扱う。

確かめるコマンドは次のとおり。

```sh
git remote get-url origin
git log --format='%h %an <%ae> / %cn <%ce>' @{u}..HEAD   # push の前（上流ブランチが無ければ「1」の範囲）
git config user.name; git config user.email                # コミットの前
git log --format='%h %an <%ae> / %cn <%ce>' @{u}..HEAD   # コミットの前にも、まだ送っていない既存のコミットを見る
gh repo view --json visibility,owner                       # 業務側の公開範囲
```

- 作者（`%an`）だけでなくコミッター（`%cn`）も見る。rebase や cherry-pick でコミッターだけが変わることがある。
- 業務側のリポジトリが `PUBLIC` になっていたら止める。
- 業務側で `gh repo view` が失敗した場合（GitHub にリポジトリが無い、権限が無い）は、公開範囲を確かめられないものとして push の前に止め、利用者に確かめる。
- `gh` が業務のアカウントでだけログインしている場合、個人のアカウントのリポジトリでは `gh repo view` が失敗することがある。個人側は公開範囲を問わないため、名義だけを確かめればよい。
- 個人の名義は、ID 付きの noreply（`<ID>+<アカウント名>@users.noreply.github.com`）だけを許す。ID 無しの noreply（`<アカウント名>@users.noreply.github.com`）は許さない。アカウント名を変えても使い続けられるのは ID 付きの形だけである。

### 4.1 予防の設定

`~/.gitconfig` の `includeIf` で、remote の URL が個人のアカウントのリポジトリでは名義を自動で切り替えられる。設定の有無と切り替え先は上書きファイルに書く。

```ini
[includeIf "hasconfig:remote.*.url:git@github.com:<個人のアカウント>/**"]
	path = ~/.gitconfig-personal
```

remote を付ける前の最初のコミットには効かないため、本 Skill の確認で止める。直し方は「6」の名義の誤りの行に従う。

## 5. リポジトリの作成と公開範囲の変更

リポジトリの作成と公開範囲の変更は、外部への公開である。

- 業務のアカウントの名義で公開リポジトリを作らない。
- 組織の中にリポジトリを作るのは、利用者に指示されたときだけ行う。
- `gh repo create` と `gh repo edit --visibility` は、作成先・名前・公開範囲を会話で示し、確認を得てから実行する。
- 公開リポジトリを作るのは個人のアカウント側だけである。最初のコミットの前に「4」の名義を設定する。

## 6. 見つかったとき

止めて、次を報告し、利用者の指示を待つ。勝手に直さない。

1. 見つけた場所（ファイル・行・コミット）と種類。秘匿情報の値は報告でも一部を伏せる（先頭4文字だけ見せる等）。
2. 直し方の案。

| 状況 | 直し方の案 |
| --- | --- |
| まだコミットしていない | 値を中立なダミーに置き換える、ファイルを `.gitignore` に入れてステージから外す（`git restore --staged <ファイル>`） |
| コミット済みで push 前 | 直してから `git commit --amend`。複数のコミットにまたがる場合は fixup と rebase（Skill `git-conventions` の「4」） |
| 名義の誤り（push 前） | リポジトリ単位で名義を設定し、`git commit --amend --reset-author --no-edit`。複数なら `git rebase --exec 'git commit --amend --reset-author --no-edit' <起点>`。ルートコミットを含む場合は `<起点>` の代わりに `--root` を使う |
| push 済み | 履歴の書き換えは force-push を伴うため、本 Skill では行わない。秘匿情報なら、まず値の無効化（キーの再発行など）を案として出す |

コミット以外の経路（メモリ・会話・公開・送信）で漏れた場合の手順と、作業の中で秘密情報・個人情報を扱う規則は Skill `security-rules` に従う（2026-10-06 追加）。
