# 業務資料の書き方

> **画面に表示する文言（HTML・ボタン・エラーメッセージ・サービスが利用者へ送るメール）は本 Skill の対象外。**
> そちらは Skill `ui-text` を使う。読み手がエンドユーザーであり、文体規則が逆になる
> （資料は常体・詳しく、画面文言は敬体・短く）。**表記は両者とも JTF 日本語標準スタイルガイドに従う。**
>
> メールの担当は送り手で分ける（2026-10-02 決定）。業務の連絡として人が送るメール（関係者への依頼・報告・社外向けの通知文）は本 Skill、サービスが利用者へ自動で送るメール（登録完了・申込受付等）は `ui-text` が担当する。

資料は**社外・社内の関係者がレビューし、意思決定の根拠にするもの**である。
利用者ごとの運用や参照先は、上書きファイル `~/.config/claude-skills/doc-writing.local.md` に書く。このファイルがあれば読んで従う（本文と食い違う箇所は上書きファイルを優先する）。無ければ本文の既定で進める。
会話の読みやすさより、**正確さ・追跡可能性・レビューのしやすさ**を優先する。

## 0. 最初に守る大原則

1. **会話の口調・キャラクター・絵文字を資料に持ち込まない。**
   セッションでどんな出力スタイルが有効でも、資料の本文は業務文書として書く。
   リポジトリに残るもの（コメント・命名・コミットメッセージ）に口調を持ち込まない原則を、資料へ拡張したもの。
2. **根拠のない記述を書かない。** 書けないなら「未確定」として残す。埋めるために推測で埋めない。
3. **迷ったら判断基準は1つ。** 「この文のまま関係者へ提出してレビューに出せるか」。

## 1. 文体

### 基本

- **常体（だ・である調）で断定的に書く。** 「〜と考えられます」「〜かと思います」は使わない。
  文末は「〜する」「〜である」「〜しない」で終える。
- **敬体（です・ます調）を使うのは、宛先が明示された文書だけ。**
  Backlog コメント・業務連絡のメール文面・社外向け通知はこちら。1つの文書内で混在させない。
- **一文を短くする。** 1文1論点。接続助詞で3つ以上つなげない。
- **主語を省かない。** 誰が・どのシステムが・どのバッチが実行するのかを明示する。
- **体言止めは箇条書きの見出しだけに限る。** 本文では動詞で言い切る。

### 使ってはいけない表現

| 禁止 | 理由 | 代わりに |
| --- | --- | --- |
| 「承知いたしました」「〜させていただきます」等の前置き | 資料に応答は不要 | 削除する |
| 「基本的に」「原則として」（例外を書かない場合） | 例外の有無が読み取れない | 例外を明記する。無いなら断定する |
| 「適宜」「必要に応じて」「柔軟に」 | 誰がいつ判断するのか不明 | 判断者と条件を書く |
| 「〜かもしれない」「〜と思われる」 | 事実か推測か不明 | 「未確定」と明記し、確認先を書く |
| 「なるべく」「できる限り」 | 検証できない | 数値または達成条件を書く |
| 「基本的な機能」「一般的な構成」 | 中身が特定できない | 機能名・構成要素を列挙する |
| 絵文字・顔文字・感嘆符の連打 | 業務文書に不適切 | 削除する。強調は太字で足りる |
| 「簡単に」「すぐに」「問題なく」 | 工数と難易度の判断を誤らせる | 前提条件と所要を書く |
| 「※ 注意」の多重ネスト | 本文が読めなくなる | 本文へ昇格するか、注記を1段に整理する |

### 強調の作法

- **太字は結論・判断・警告にだけ使う。** 段落の大半が太字だと強調が機能しない。
- 読み手が判断を誤ると手戻りが発生する箇所には、引用ブロックで警告を置く。
  例: `> **【警告】4.3 の API パスは実装と食い違っている（2026-08-26 注記）。**`
  警告の目印には絵文字（`⚠️` 等）を使わず、`【警告】` と文字で書く（2026-10-02 変更）。
- 未確定・要確認は本文に埋めず、**一覧表に集約して番号を振る**（後述の記号体系）。

### 用語

- **社内で使われている呼び方に合わせる。** 一般語に言い換えない（例: 「特典会」を「イベント」に置き換えない）。
- **1つの対象を1つの語で呼ぶ。** 同じものを「会員」「ユーザー」「顧客」と混ぜない。冒頭で用語を定義する。
- 略語・専門用語は**初出でかっこ書きの一言説明**を添える。以降は略語のみで通す。
- 環境は必ず明示する（本番 / 検証 / ローカル）。「サーバー」だけで済ませない。
- ダミー値・サンプルは中立な名前を使う（`test_user_01` / `山田太郎` など）。作品名・キャラクター名は使わない。

## 2. 構成

### 冒頭に必ず置くもの

1. **タイトル**（何の資料かが単体でわかる名前）
2. **メタ情報の表** — 対象課題（URLつき）／対象リポジトリと調査コミット／関連文書へのリンク／作成日・最終更新日／**状態**
3. **状態には「今この資料をどう扱えばよいか」を書く。**
   例: 「大半が合意済み。実装を止める確認事項は残っていない」「一部確定。残りは未着手」
4. **本書の目的**を1〜3文。「本書は、〜するにあたり、〜を定義する」。
5. 3階層以上ある資料には**目次**（アンカーリンク）を置く。

### 記号体系（複数の性質の記述が混ざる資料では必須）

事実・決定・未確定を文中で混ぜると、レビュアーが何に合意すべきか判断できなくなる。
先頭で記号を定義し、以降その記号で呼ぶ。

| 記号 | 意味 |
| --- | --- |
| 要件 | 課題・コメントで明文化済み。合意済みとして扱う |
| D-n | 設計上の決定事項。合意状況を表で個別に示す |
| Q-n | 関係者への確認事項。解決済み／先行設計中／保留を明示する |
| C-n | 移行先・既存基盤が課す制約 |
| P-n | 現状の不具合と改善提案（本筋と分けて付録へ） |

- **記号は資料をまたいで再利用しない。** 別資料と番号が食い違ったら、
  冒頭に警告を置き「本書の番号を正とする」と宣言し、対応表の在り処を示す。
- 章末または巻末に **決定事項一覧・未決事項一覧**を表で置く。本文を読まずに残件が把握できる状態にする。

### 進捗の表し方

- 確定した項目は `- [x]`、未確定は `- [ ]` のままにする。**未確定を消して隠さない。**
- 確定項目には**確定した日付**を添える（例: `（2026-08-04 確認）`）。
- 覆った判断は、**元の記述を消さずに訂正の経緯を残す。**
  例: 「当初『8本』と申告されたが、実績を確認したところ根拠がなかったため訂正」
  → 後から同じ議論が再燃したときに、これが唯一の防波堤になる。

### 資料ごとの標準構成

- **要件定義書**: 背景と目的 / 対象範囲（やらないことも書く） / 前提条件と制約 / 機能要件 / 非機能要件 / 移行要件 / 試験要件 / 決定事項一覧 / 未決事項一覧
- **現状調査書（as-is）**: 調査対象と調査時点のコミット / 全体構成 / 処理の流れ / データ構造 / 外部依存 / 判明した不具合 / 未調査の範囲
- **設計書**: 方針と選定理由（**採用しなかった案とその理由も書く**） / 構成図 / インターフェース / データ設計 / 影響範囲 / 移行手順とロールバック / 未確定事項
- **調査報告**: 問いの定義 / 結論（先に書く） / 根拠 / 検証方法と再現手順 / 限界と未検証の範囲
- **運用手順書・デプロイ手順**: **書く前に、対象リポジトリの `README.md`・`package.json` の scripts・`.github/workflows/` を読み、そこに書かれた手順・コマンド・文体に合わせる。** 独自の手順を組み立てない（2026-10-02 追加。「README 準拠で出して」「README を参考にしてる？」と2つのリポジトリで差し戻しを受けたため）
- **議事録**: 日時・出席者 / 決定事項 / 保留事項と次アクション（担当と期限） / 議論の要旨
- **Backlog 貼り付け用**: 元資料と別ファイルにする。リンクは絶対URL。投稿後は投稿先コメントIDを元資料に記録する。

## 2.5 設計書

本節は、関係者へ提出してレビューを受ける設計書を対象とする。
GitHub Issue から PR を作る流れでレビュー用に書く短い Design doc は、Skill `design-and-ship` の書式に従う（2026-10-02 決定）。

**設計書の価値は「何を作るか」ではなく「なぜその形にしたか」にある。**
何を作るかはコードを読めば分かるが、なぜそうしたかはコードに残らない。
半年後に別の人が仕様変更を検討するとき、判断の前提が分からず作り直しになる。

### 必ず書く章

1. **目的と対象範囲** — この設計が満たす要件へのリンク。**やらないことを明記する。**
2. **前提と制約** — 既存基盤が課す制約（C-n）、変えられないもの、決定の期限。
3. **方針と選定理由**
   - **採用した案と、採用しなかった案を両方書く。** 却下理由が本体。
   - 比較軸を表にする（実装量 / 運用負荷 / 費用 / 既存との整合 / 可逆性）。
   - 「既製サービスで足りるのに自作した」等、疑問を持たれる選択には理由を先に書く。
4. **全体構成** — 構成図（Mermaid 等）と、図に出てくる要素の役割を1行ずつ説明する。
   **図だけ置いて説明を省かない。** 図は関係を示すもので、判断は本文に書く。
5. **インターフェース** — API のパス・メソッド・リクエスト・レスポンス・**エラーとステータスコード**。
   認証方式と必須ヘッダーを漏らさない。
6. **データ設計** — テーブル・カラム・型・NULL 可否・既定値・インデックス・**キーの対応関係**。
   FK 制約がない自然キー結合があるなら、それを明記する（暗黙の前提は必ず事故になる）。
7. **処理フロー** — 正常系だけでなく**異常系・リトライ・冪等性**を書く。
   同じリクエストが2回来たらどうなるかを必ず書く。
8. **影響範囲** — 変更で壊れうる既存機能、同じテーブル・API を使っている箇所を列挙する。
9. **移行手順とロールバック** — 手順は番号付きで、**各手順に「戻し方」を添える。**
   戻せない手順（データ削除・不可逆なマイグレーション）は**戻せないと明記する。**
10. **環境ごとの差分** — 本番 / 検証 / ローカルで異なる値・設定・制約。
11. **未確定事項** — 設計を止めている項目と、確認先。

### 設計書で落としやすい項目

- **エラー時の挙動。** 正常系だけの設計書はレビューを通っても実装で必ず詰まる。
- **権限。** 誰がその操作を実行できるのかを書く。
- **上限と性能。** 件数・サイズ・タイムアウト・同時実行数の想定値。
- **ログと監視。** 障害時に何を見るのかを設計時点で決める。
- **冪等性と再実行。** バッチ・キュー・Webhook を扱うなら必須。
- **不可逆な操作の洗い出し。** 本番で実行する前提の手順は、可逆・不可逆を明示的に分類する。

### 実装と食い違ったとき

**資料を黙って実装に合わせて書き換えない。** どちらが正かは書き手が決めることではない。
冒頭に警告を置き、食い違いの内容・両者の主張・判断待ちであることを明記する。

## 2.6 報告書

報告書は**読み手が結論だけ読んで判断できること**が最優先。経緯は後ろに置く。

**事実を調べて書く資料（調査報告書・現状調査書・障害報告書など）は、調べ始める前にプロジェクトのナレッジを引く**（2026-10-06 追加）。
ナレッジ検索の道具（会話の開始時に案内が出るもの）がある場合は、対象の用語で検索し、0件なら語を変えて2〜3回（別の用語・英語と日本語・略語・関連する症状）試す。それでも0件なら知識なしとして扱い、推測で埋めない。ヒットは要約なので、使う前に全文を読み、資料の根拠にするなら実物でも確かめる。
調べて新しく分かったことは結論を1行の題にして登録し、誤った知識を見つけたら訂正を付ける。道具の具体的な使い方は上書きファイルに書く。

### 調査報告書

1. **問い** — 何を明らかにするための調査か。1〜2文。
2. **結論** — **最初に書く。** 「〜である」と言い切る。言い切れないなら「断定できない」と書く。
3. **根拠** — 結論を支える事実のみ。**コードならファイルパスと行番号、
   実データなら取得日と取得方法（クエリ・コマンド）を書く。**
4. **検証方法と再現手順** — 第三者が同じ結果を得られる形で書く。
5. **限界** — 調べていない範囲、確認できなかったこと。**ここを書かない報告書は信用されない。**
6. **推奨アクション** — 選択肢を並べて終わらせない。**推奨を1つ出し、理由を書く。**

### 障害報告書

読み手（顧客・上長）が知りたい順に並べる。

1. **概要** — 何が、いつから いつまで、誰に、どの範囲で起きたか。1段落。
2. **影響範囲** — 影響を受けた機能・件数・データ。**影響がなかった範囲も書く**（不安の切り分けになる）。
3. **時系列** — 発生・検知・一次対応・復旧の各時刻。**検知が遅れたならその時刻も隠さず書く。**
4. **直接原因** — 技術的に何が起きたか。
5. **根本原因** — なぜそれが起きたか、なぜ事前に防げなかったか。
   **個人の不注意で終わらせない。** 仕組みで防げなかった理由まで掘る。
6. **暫定対応と恒久対応** — それぞれ、実施済みか予定かを明示し、予定には期限と担当を書く。
7. **再発防止策** — 検証可能な形にする。「注意する」「気をつける」は対策ではない。

- **推測を事実として書かない。** 原因が特定できていないなら「特定できていない」と書き、
  調査中の仮説は仮説として分ける。
- **数値は必ず出典を添える。** 影響件数はクエリと実行日時を残す。

### 進捗・作業報告

- **完了・未完了・詰まっている点の3つに分ける。**
- **「完了」と書くのは検証を通したときだけ。** 未検証なら「実装済み・未検証」と書き分ける。
- 詰まっている点は、**解決してから報告するのではなく、詰まった時点で書く。**

## 3. 事実と推測を分ける

- **コードを根拠にした記述には、ファイルパスと行番号を書く。** 「〜のようだ」では書かない。
- **実データを根拠にした記述には、取得日と取得方法を書く**（例: 「実DBの `information_schema` から生成。2026-08-06 時点」）。
- **未検証は未検証と書く。** 「動作するはず」は書かない。「起動は実測で確認。完走は未検証」のように分ける。
- 数値は出典を書く。概算なら「約」を付け、算出根拠を併記する。
- 図（Mermaid 等）は本文の代わりにしない。図で構造を示し、判断は本文に書く。

## 4. レビューを想定した書き方

- **結論を先に書く。** 経緯は結論の後。読み手は全部読まない。
- 読み手が最初に知りたいのは「**自分は何を判断すればよいか**」。それを状態欄と未決事項一覧に集約する。
- クリティカルパス（これが決まらないと止まる項目）を明示する。
- 関連資料は相対リンクで相互に張る。片方向にしない。
- 長い資料には**要約版を別ファイルで用意する**（`-short` 等）。要約版と本体で内容を食い違わせない。

## 5. 提出前チェック

書き終えたら、以下を上から順に確認する。1つでも該当したら直す。

- [ ] 会話用の口調・キャラクター名・絵文字が本文に残っていないか
- [ ] 敬体と常体が混在していないか
- [ ] 「適宜」「基本的に」「なるべく」「〜と思われる」が残っていないか
- [ ] 同じ対象を複数の呼び方で呼んでいないか
- [ ] 根拠のない断定がないか（コード根拠にはパスと行番号、実データには取得日）
- [ ] 未検証を検証済みのように書いていないか
- [ ] 未確定事項が本文に埋もれず、一覧表に集約されているか
- [ ] 環境（本番 / 検証 / ローカル）が特定できる書き方になっているか
- [ ] 太字が多すぎて強調が機能しなくなっていないか
- [ ] 作成日・最終更新日・状態が更新されているか
- [ ] リンクが切れていないか（相対パス・アンカー）
- [ ] 一文が100文字を超えていないか／読点が4個以上ないか
- [ ] 見出しに句点（。）が付いていないか
- [ ] 箇条書きの中で文体と句点の有無が混ざっていないか
- [ ] 表記が JTF 日本語標準スタイルガイドに従っているか（長音・全角半角の間のスペース・日付の形式・記号）
- [ ] リンクテキストが「こちら」になっていないか

## 6. 既存資料に加筆するとき

- **その資料の既存の文体・記号体系・章番号にこちらが合わせる。** 自分の型を持ち込まない。
- 記号（D-n / Q-n）を追加するときは、既存の最大番号の続きから振る。**欠番を埋めない。**
- 既存の記述と食い違う内容を書く場合、消す前に食い違いを明示する。判断は書き手が勝手に下さない。
- 更新したら**最終更新日と状態欄を必ず直す。** ここが古いままの資料は信用されなくなる。

## 7. Skill `yomiyasu` との併用

Skill `yomiyasu`（文章を読みやすく書き直す規則）を導入している場合は、資料の本文は本 Skill の規則に従い、文の組み立てに `yomiyasu` の規則を重ねて書く。
両者が食い違う箇所は本 Skill を優先する。調停用の Skill `yomiyasu-local` があれば、その「2. 資料」に従う。

## 参考になる実例

新規に型を起こす前に、同じリポジトリまたはチームの既存の資料（例: `docs/` の要件定義書）を読み、書式を合わせる。見るとよい点は次のとおり。

- メタ情報表・記号体系・警告注記・一覧表の作り
- チェックボックスによる確定管理・訂正の経緯の残し方・費用対効果の書き方
