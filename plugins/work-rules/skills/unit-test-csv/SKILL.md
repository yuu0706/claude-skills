# 単体テスト項目の TSV 出力

対象コードの単体テストケースを洗い出し、スプレッドシートへ取り込める**タブ区切りの `.tsv` ファイル**として書き出す。

## 手順

1. 対象と観点を特定する（**このSkillを呼ぶ前の会話を最優先の情報源にする**）
   - このSkillが実行される**前の会話の流れ**を必ず参照し、そこで話題になっていた対象・仕様・要件・懸念点・既に挙がったテスト観点を拾い上げてケースの土台にする。
   - 会話で対象コード（ファイル・関数・メソッド・クラス・機能）が特定できていればそれを読む。
   - 会話から対象が判然としない場合のみ、対象候補を提示して確認する。
   - 会話で言及された仕様・エッジケース・期待挙動は、コードから読み取る内容よりも優先してケースに反映する。

2. テストケースを洗い出す
   - 洗い出す前に、プロジェクトのナレッジを引く（2026-10-06 追加）。確認表の作り方に関する過去の決定や、対象の落とし穴が残っていることがある。ナレッジ検索の道具（会話の開始時に案内が出るもの）がある場合は、対象の機能名と「確認表」「テストケース」などの語で検索し、0件なら語を変えて2〜3回（別の用語・英語と日本語・略語）試す。それでも0件なら知識なしとして扱い、推測で埋めない。ヒットは要約なので全文を読んでからケースに反映する。新しく決めたことは結論を1行の題にして登録する。道具の具体的な使い方は上書きファイル `~/.config/claude-skills/unit-test-csv.local.md` があれば読んで従う。
   - まず**会話で挙がった内容**をケース化し、その上で対象のロジックを読み、以下を漏れなく補完する:
     - **正常系**: 代表的な入力、境界値の内側、典型的なユースケース。
     - **異常系**: null/空/未定義、境界値の外側、型不正、権限・認証エラー、例外・エラー処理、重複、上限超過など。
   - 分岐（if / switch / early return / try-catch）と境界値は必ずケース化する。
   - 大項目→中項目→小項目は、機能の階層で整理する（例: 大=「ユーザー登録」/ 中=「メールアドレス検証」/ 小=「形式チェック」）。

3. 出力する
   - **成果物は `.tsv` ファイルとして書き出す。** 会話へコードブロックを貼るだけで終わらせない。
     件数が増えると端末からのコピーで崩れるため、ファイルにしてスプレッドシートへ取り込ませる。
   - 保存先は作業対象のリポジトリ直下、ファイル名は内容が分かる英数字（例: `testcase-<対象>.tsv`）。
     リポジトリへ置かない指示があるときだけ scratchpad に置く。
   - **ファイルはスクリプト経由で書き出す**（Python の `"\t".join(...)` など）。
     手打ちの文字列はタブが空白へ化けるため、区切り文字を明示的に組み立てる。
   - 下記の列順で、**タブ区切り**のデータ行を書き出す。
   - **ヘッダー行（カラム名）は出力しない**。データ行のみを出す。
   - 会話には**ファイルパスと件数（正常・異常の内訳）を伝える**。全件を本文へ貼り直さない。

## 列（この順・このヘッダーで固定）

| 列 | 内容 |
|----|------|
| 番号 | 1 から連番 |
| 大項目 | そのテストの種別（例：「チケットの付与」）。テストの大きなくくり。 |
| 中項目 | テスト対象箇所がシステム内でどのような立ち位置・役割なのか、または（異常系の場合）どんな障害内容か。 |
| 小項目 | テストの場合わけ（そのケースがどの条件・パターンに該当するか）。 |
| 正常系異常系 | `正常` または `異常` のいずれか。**必ずこの2値のみ**（「系」を付けない・他の表記も禁止）。スプレッドシートのプルダウン選択肢と完全一致させるため。**判定は与える入力・状態で決める**（不正・想定外・失敗を与えるなら `異常`、正しい入力と正規の操作なら `正常`）。期待値がエラーメッセージでも、入力が正しければ `正常` にはしない。表の中で基準を混ぜない（2026-10-05 決定）。 |
| ケース内容 | テスト内容の詳細（どんな入力・操作・条件でテストするかを具体的に書く）。**実施する手順もここへ書く**（下記）。 |
| 期待値 | テストの結果の期待値（例：「ログが出力されること」）。そのケースで期待される結果・振る舞いを書く。 |

### 複数リポジトリで同じ対応をしているとき

**同じ作業を複数のリポジトリで並行して行っている場合、大項目にはリポジトリ名を入れる。**
各リポジトリの表は最終的に1枚のシートへまとめるため、**大項目で出所を絞り込めないと使えなくなる。**
1リポジトリ単体では観点を大項目に置くほうが読みやすいが、それは採らない。

- 大項目: リポジトリ名。組織共通の接頭辞（例: `example-`）を落とした短い名前で統一する（例: `example-order-api` は `order-api`）。全行が同じ値になる。
- 中項目: 検証のフェーズ（例: `デプロイ` / `ランタイム確認` / `API疎通` / `入力検証` / `リグレッション` / `ロールバック`）。
  **他リポジトリの表と語彙を揃える。** 既存の表があるなら、そこで使われている語をそのまま使う。
- 小項目: 対象と場合わけを**中黒でつなぐ**（例: `appUserAuth・未登録の利用者` / `Layer・アタッチ`）。

観点を大項目に置いた表を直すときは、**列を1段ずつ下へ送る**（大項目→中項目、中項目→小項目の先頭）。
情報が落ちないので作り直しは不要である。

### ランタイムやライブラリの更新に伴う動作確認の表（2026-10-02 追加）

**ランタイム（nodejs24 等）やライブラリの更新に伴う動作確認の表は、更新の影響を確かめる観点に絞る。**
コードの分岐を網羅する単体テストの観点は持ち込まない。

- 異常系は入れない。全行を `正常` とする。
- 中項目は `インフラ確認`（スタックの状態、関数の一覧とランタイムの値）と、更新の対象の関数ごとの `Lambda実行` で組む。
- 手順は、デプロイ後に実際に叩けるもの（コンソールでの確認、`aws lambda invoke`）だけにする。

背景: ランタイムの移行で、複数のリポジトリで「異常系はなくていい。Lambda の動作確認を目的にしてほしい」「範囲が広すぎる」と同じ差し戻しを受けた。

### 単体テストの実行は確認表に入れない（2026-10-05 指示）

**CI がデプロイの前段で単体テストを流しているなら、その実行を確認表の行にしない。**
デプロイできたことが合格を意味するため、人手で二度やらせることになる。
確認表の実施者は内部の知識を持たない前提であり、テストランナーの出力から合否を判断させるのも適切でない。

- **まず CI を読む。** `.github/workflows/` にテストの実行があるかを確かめてから判断する。
- **単体テストでしか見ていない要件があれば、行を消すだけにしない。** 実物を見る行へ置き換える
  （例: 組み立てた文字列を検査する代わりに、届いたメールを開いて確認する）。実物のほうが証拠として強い。
- **置き換えずに消す場合は、確認表から落ちた要件を資料へ書き残す。**

### 画面に版が複数あるとき（2026-10-05 決定）

**全項目を版ごとに2倍にしない。版によって変わるところだけを版ごとに分ける。**

- **先にコードで差分を数える。** 版で分岐する処理と、分岐するのが見た目だけの箇所を分けて数える。
  分岐が無い処理（入力検証・画面遷移・保存など）は、どちらか一方の版で実施すれば足りる。
- **版ごとに分けるのは3種類。** 分岐する値そのもの（リンク先・文言）、見た目を目で見る実機の項目、
  現行と見比べる項目（比較相手が版ごとに別のため）。
- **小項目に版を書く**（例: `表示の崩れ（Web版）`）。書いていない行は既定の版で実施する、と会話で伝える。

### ケース内容には実施手順まで書く（2026-10-02 指示）

**何を確かめるかだけでなく、どうやるかを書く。** 読んだ人が手順を自分で調べ直すのは手間であり、
調べ方が人によって変わると結果も揃わない。列は増やさず、ケース内容の中へ入れる。

- **道具と対象を名指しする。** 実行するコマンド（`pnpm jest <テストファイルのパス>` / `curl` の1行）、
  開くURL、操作する画面の要素、確認する場所（開発者ツールのどのタブか）。
- **画面の項目は、画面に表示される文言で書く（2026-10-07 指示）。** 設定ファイルの内部の名前で書かない。
  例: GitHub Actions の Run workflow の入力欄は、`inputs` のキー名（`branch`）ではなく `description` の文言（「Branch to deploy (web/api)」）が表示される。
  書く前に、表示される文言を設定やコードから確かめる。
- **行だけで実施できるようにする。** 「上記と同じ手順で」のように前の行へ依存させない。
  直前の行を受ける場合も、何を受けるのかを1語で添える。
- **事前準備の行を作らない。関数や変数に頼らず、コマンドは各行で全文を書く（2026-10-07 指示）。**
  「関数を定義する」「ID を変数に入れる」といった事前準備の行を置くと、行だけで実施できなくなり、
  事前準備をテストケースに含めたくない利用者の意向にも反する。インスタンス ID のように環境で変わる値は、
  コマンドの中で名前やタグから引く（例: `aws ec2 describe-instances --filters "Name=tag:Name,Values=<Name タグ>"` で
  ID を引く処理を、同じコマンドの中に埋め込む）。
- **他の行を番号で指さない（2026-10-07 指示）。** 「No.3 の実行画面で」「No.2 で控えたパス」のように書くと、
  利用者が表の番号を振り直したときに、指している行を全部直す手間ができる。
  受けるものは中身で呼ぶ（例: 「手動実行したワークフローの実行画面で」「デプロイ後に確認したアプリの版番号」「ワークフローの実行結果の時刻」）。
- **既にテストがある項目は、テスト名を指す。** CI が流していない（前節の対象外の）単体テストを行にする場合に限る。
  「引数に空文字を渡す」のように書くと、実施者がテストコードを書く作業だと受け取って手が止まる。
  対象のテストファイルを実行し、どのテスト名の結果を見るのかを書く。
  対応するテストが見つからない項目は、その時点でテストが無いと分かるので、書く前に探す。
- **行の中で、定義していない名前を使わない。** `-d @body.json` のようにファイル名だけ書くと、
  実施者は中身を知らないため送れない。**入力はコマンドへ直接埋め込み、変える値も埋め込んだ完成形にする。**
  必須項目だけに絞れば1行に収まる（任意項目は、その項目を試す行にだけ足す）。
  数百文字の値など埋め込むと読めなくなるものだけ、生成するコマンドを本文に書いてからファイルへ渡す
  （例: `python3 -c "..." > /tmp/body.json` を実行してから `curl ... -d @/tmp/body.json`）。
  別ファイルを用意して参照させる形は採らない。表とファイルがはぐれると、行だけでは実施できなくなる。
- **書いたコマンドは、実際に打って通る形か確かめる。** とくに引用符の入れ子が壊れやすい。
  `python3 -c "..."` の中に二重引用符の JSON を入れるとシェルがそこで文字列を切るため、
  内側は単引用符にする。確認表を書き終えたら、コマンドを含む行を実際に実行して構文を通す。
- **可変の識別子を直書きしない。** 作り直すと変わる値（API の ID、ARN、エンドポイントのドメイン）を
  本文へ埋め込むと、次のデプロイで表が嘘になる。確認済みの値を使う場合は、それを確かめた行を番号ではなく中身で指す（例: 「事前準備で控えたインスタンス ID」）。
- **文章に環境を書かない。** この Skill が作る表は検証環境での確認を前提とするため、
  「検証環境の」「検証アカウント ○○」「リージョン ○○」といった断りを本文へ書かない（2026-10-05 指示）。
  **コマンドの中は別で、`AWS_PROFILE` や `--region` はそのまま残す。**
  これらが無いと既定のプロファイルで動き、本番を叩く事故につながる。
- **値は作り方まで書く。** 「501文字」ではなく `python3 -c "print('あ'*501)"` のように再現できる形にする。
- **元へ戻す必要がある手順は、戻すことまで書く。** 定義ファイルや環境変数を一時的に変える確認が該当する。
- 全行に共通する前提（接続先・認証情報）は、毎行へ繰り返さず会話で伝える。

## 出力ルール

- 表記（長音・全角半角・数字・記号）は JTF 日本語標準スタイルガイドに従う。

- 区切り文字は**タブ**（カンマではない）。ユーザーがカンマ希望と言った場合のみCSV（カンマ区切り）にする。
- セル内の値にタブ・改行を含めない。長い説明は簡潔に1行でまとめる。
- **ヘッダー行（カラム名の行）は出力しない**。1行目からデータ行を出す（貼り付け先に既にヘッダーがある前提）。
- **結果の記入欄（「結果（STAGING）」など）は出力しない。** 貼り付け先のシートに既にあるため、付けると列がずれる（2026-10-02 指示）。
- ケース数が多い場合も省略せず全件出力する。省略が必要なほど多いときは、その旨を先に伝えてから出す。
- 拡張子は `.tsv`。カンマ区切りにした場合のみ `.csv` にする。
- **書き出したら必ず検証してから報告する。** 目視で済ませない。
- **検証は `python3` で行う。`cut` / `awk` / `sort` / `uniq` を使わない。**
  macOS 標準の `cut` と `awk` は、日本語を含む TSV で列の値を誤って返す（実測）。
  しかも `NF` は全行同じ値を返すため、列数の検査だけは通ってしまい気付けない。

  ```
  python3 - <<'EOF'
  rows = [l.rstrip("\n").split("\t") for l in open("<file>", encoding="utf-8")]
  print("行数", len(rows))
  print("列数", sorted({len(r) for r in rows}))          # [7] になること
  print("5列目", sorted({r[4] for r in rows}))            # ['異常', '正常'] のみ
  print("正常", sum(r[4] == "正常" for r in rows), "異常", sum(r[4] == "異常" for r in rows))

  # 行だけ読んで実施できるかの検査。いずれも 0 件になること
  import re
  for label, pat in [("前の行への依存", r"上記|同上|同じ手順|前述"),
                     ("未定義の名前", r"<[^>]{1,20}>"),
                     ("値が決まっていない", r"適宜|任意の"),
                     ("他の行の番号", r"No\.\s?\d|番号\d")]:
      print(label, [r[0] for r in rows if re.search(pat, r[5] + r[6])])

  # バッククォートで囲んだコマンドの構文検査と、埋め込んだ JSON のパース検査
  import subprocess, json
  SHELL_HEAD = ("curl", "python3", "aws", "AWS_PROFILE", "for ", "diff", "pnpm", "cd ", "npm", "node ")
  for r in rows:
      for cmd in re.findall(r"`([^`]+)`", r[5]):
          if not cmd.startswith(SHELL_HEAD):   # JavaScript の断片などは対象外
              continue
          if subprocess.run(["bash", "-n", "-c", cmd], capture_output=True).returncode:
              print("構文エラー", r[0], cmd[:80])
      for payload in re.findall(r"-d '(\{.*?\})'", r[5]):
          try:
              json.loads(payload)
          except Exception:
              print("JSONが壊れている", r[0])
  EOF
  ```

## 出力例（イメージ）

ヘッダー行は付けず、1行目からデータ行を書き出す（列順は上表のとおり）。
以下はファイルの中身のイメージであり、会話へ貼る形ではない。

```text
1	ユーザー登録	メール検証	形式チェック	正常	正しい形式のメールアドレスを入力	バリデーションを通過し登録される
2	ユーザー登録	メール検証	形式チェック	異常	@を含まない文字列を入力	形式エラーを返す

```

## サンプル（参考）

実際の案件の型を引き継ぎ、架空のサービスで作り直した出力例が `examples/` にある。**列の使い分け・粒度・書き方に迷ったときに参照する**（毎回読む必要はない）。傾向の違う2種類を用意している。

### `examples/sample.tsv` — API 疎通確認型

複数サービスの API 疎通・インフラ確認を洗い出したもの。主な特徴:

- **大項目** をサービス単位（`order-api` / `member-api` / `リグレッション`）で分けている。
- **中項目** で「インフラ確認」「API」「非HTTP」などの立ち位置を分類している。
- **小項目** に API 関数名などの具体的な対象を書いている。
- **ケース内容** に実行する `curl` コマンドやリクエストボディを 1 行で具体的に記載している（改行を入れない書き方の実例）。

### `examples/sample2.tsv` — 機能・振る舞い型

ある機能（異常停止時の部屋の作り直し・ログ記録）の振る舞いを洗い出したもの。主な特徴:

- **大項目** を機能の観点（「〜で作り直し」「作り直しをしない条件」「記録される内容」「動作への影響」「既存機能への影響」など）で分けている。
- **正常/異常** の振り分けの実例（判定の基準は上の列の表に従う。このサンプルは基準を明文化する前のものなので、振り分けそのものは参考にしない）。
- **ケース内容** を発生させる状況、**期待値** を記録内容・再接続の有無などで具体的に書いている（非エンジニアにも読める粒度の実例）。
