# design-and-ship

GitHub Issueで依頼された機能について、以下の手順で対応してください。

1. Issueの内容を読み、実装すべき機能を理解する
2. 利用者が決めていない判断（実装方針・対象範囲など）が残っていれば、利用者に質問し、答えを得てから次へ進む（Skill `grilling` を導入していれば、その進め方で質問する）
3. どのように設計するかを検討し、Design docとしてまとめる
   - 検討と調査を始める前に、過去の決定事項と落とし穴をプロジェクトのナレッジから引く。ナレッジ検索の道具（会話の開始時に案内が出るもの）がある場合は、対象の用語で検索し、0件なら語を変えて2〜3回（別の用語・英語と日本語・略語・関連する症状）試す。それでも0件なら知識なしとして扱い、推測で埋めない。ヒットは要約なので、使う前に全文を読む
   - 設計で新しく決めたことと見つけた落とし穴は、結論を1行の題にしてナレッジへ登録する。誤った知識を見つけたら訂正を付ける。道具の具体的な使い方は上書きファイル `~/.config/claude-skills/design-and-ship.local.md` があれば読んで従う
4. Design docに基づいて実装する。実装とテストの作成はサブエージェントへ任せ、起動は Skill `sub-agent-ops` に従う
5. サブが書いたテストの結果と動作を、メインが確認する
6. コミットまで行う。コミットの前に Skill `commit-guard` を通し、書き方は Skill `git-conventions` に従う。push とPRの作成は、利用者に指示されたときだけ、承認を得てから行う

Design docとPRは、レビューする人間が短時間で「何を・なぜ決めたか」を把握できることを最優先にする。網羅的な説明書ではなく、意思決定の記録として書く。

## Design docの書き方

Design docの構成は本節に従う。文体は Skill `doc-writing` の「1. 文体」に従い、表記は JTF 日本語標準スタイルガイドに従う。
関係者へ提出する設計書を求められた場合は、本節ではなく `doc-writing` の「2.5 設計書」に従う（2026-10-02 決定）。

- 冒頭に結論（採用した設計とその理由）を3行以内で書く。詳細はその後に続ける
- 検討した代替案は表で比較する（案・却下理由の2列で十分。メリット/デメリットを毎回文章で書き下さない）
- 採用しなかった選択肢の説明は、却下理由が伝わる最小限の長さにする
- 「やらないこと（Non-goals）」を書き、スコープ外の一般論・将来の拡張可能性の羅列は書かない
- 用語定義・背景・目的・対象読者のような定型セクションは、読み手がその技術用語を知らないと判断できる場合のみ書く。自明な場合は省略する
- 見出しは意味のある単位でのみ作る。同じ内容を複数の見出しで繰り返さない
- 迷ったら削る。書いた後に「このセクションがなくてもレビュアーは意思決定を理解できるか」を自問し、できるなら削除する

## PR descriptionの書き方

- 「何を変更したか」と「レビュアーが見るべき点」に絞る。実装の手順を逐一説明しない
- Design docへのリンクを貼り、設計の詳細はそちらに譲る（PR本文に重複させない）
- 実装ファイルの一覧など、diffを見れば分かる情報は書かない

## 避けるべき表現

冗長な語尾などの一般的な禁止表現は Skill `doc-writing` に従う。本スキル固有の禁止は次のとおり。

- 自明なメリット・デメリットの羅列（例:「コード量が増える」「可読性が向上する」だけで終わる説明）
- 同じ主張を異なる見出しで繰り返すこと
