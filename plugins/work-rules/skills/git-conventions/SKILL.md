# コミットとブランチの書き方

コミットするときは、先に Skill `commit-guard` の確認を通す。本 Skill は書き方だけを扱う（2026-10-06 作成）。
利用者ごとの運用や参照先は、上書きファイル `~/.config/claude-skills/git-conventions.local.md` に書く。このファイルがあれば読んで従う（本文と食い違う箇所は上書きファイルを優先する）。無ければ本文の既定で進める。
push は利用者に指示されたときだけ行う。コミットした後は、push するかを利用者に聞いて止まる。

## 1. 優先順位

リポジトリに独自の書き方があれば、そちらに従う。本 Skill の規則は、リポジトリに決まりが無いときの既定である。

1. リポジトリの `CLAUDE.md`・`CONTRIBUTING.md`・commitlint などの設定
2. リポジトリの既存の書き方（`git log --no-merges --format=%s -20` と `git branch -a` で確かめる）
3. 本 Skill の既定

例えば、件名の先頭に変更した対象の名前（`docs:`・`store:` 等）を付けているリポジトリがある。この形のリポジトリではそれに合わせる。

## 2. コミットメッセージ

### 2.1 既定の書式

| 項目 | 既定 |
| --- | --- |
| 構成 | 1行目の件名に What（何をどうしたか）、空行を挟んだ本文に Why（なぜ変えたか）を1〜3行で書く。Why が件名から明らかなときは本文を省く |
| `Co-Authored-By` の行 | リポジトリの既存のコミットに合わせる（`git log -20 --format=%B \| grep -c Co-Authored-By` で確かめる）。既存のコミットに無ければ付けない |
| 言語 | 日本語 |
| type の接頭辞（`feat:` 等） | 付けない |
| 課題キー・Issue 番号 | 付けない。課題との紐づけはブランチ名と PR で行う |
| 長さ | 30字以内を目安とする |
| 文体 | 業務用の硬い文章。会話の口調を持ち込まない |

- 件名を短い What に限るのは、`git log --oneline` の一覧で読める長さを保つためである。
- Why を本文に書くのは、`git log` や `git blame` から変更の理由までたどれるようにするためである（2026-10-07 指示「コミットログには Why を書く」。それまでの「件名だけ」の既定を改めた）。
- 本文に書くのは Why だけにする。How はコードに、採らなかった案（Why not）はコードコメントに書く（CLAUDE.md「コード・テスト・コミット・コメントに書くことを分ける」）。
- 長い経緯や検討の過程は、本文ではなく PR の説明や資料に書く。
- 文言だけを変える変更は、その旨を件名に書く（Skill `ui-text`）。

### 2.2 件名を短くする

件名を書いたら、次の表に当たる言葉を削る。Skill `yomiyasu`（文章を読みやすく書き直す規則）を導入している場合は、その規則も重ねて使う（調停用の Skill `yomiyasu-local` があれば、その扱いに従う）。
「何をどうしたか」だけを残す。

| 削るもの | 例 |
| --- | --- |
| 回りくどい言い方 | 「〜を行う対応」「〜するように修正」「〜において」 |
| 意味を足さない補足のかっこ | 「（対応）」「（修正）」 |
| ぼかし言葉 | 「など」「一部」「各種」 |
| 理由や経緯 | 「〜のため」「〜に伴い」。理由は本文に移す |

例: `ユーザー一覧画面において検索条件が正しく反映されない不具合を修正する対応` → `ユーザー一覧の検索条件が効かない不具合を修正`

30字に収まらないときは、件名を削る前に、1つのコミットに目的が2つ以上入っていないかを見る。入っていれば「3」に従って分ける。

利用者が件名を指定した場合は、指定どおりに使う。30字を超えるときや「削るもの」に当たるときは、削った案を1つ示し、どちらを使うかを確かめてからコミットする。

## 3. 粒度

- 1コミットに1つの目的を入れる。
- 関係ない変更（ついでの整形・別件の修正・デバッグ用の出力）を混ぜない。混ざっていたら `git add -p` 相当の操作でステージを分けるか、利用者に分け方を確かめる。
- 生成物・依存関係の更新（ロックファイル等）は、それを生んだ変更と同じコミットに入れる。

## 4. push 前の履歴の整理

| 状態 | 扱い |
| --- | --- |
| push 前のコミット | fixup・squash・amend で整理してよい |
| push 済みのコミット | 書き換えない（force-push は他者への影響が読めない） |

- push 済みかどうかは `git branch -r --contains <コミット>` で確かめる。出力があれば push 済みである。
- 対話式の操作（`git rebase -i`）は使えないため、次の形で行う。

```sh
git commit --fixup=<直したいコミット>
GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash <直したいコミットの1つ前>
```

`GIT_SEQUENCE_EDITOR=:` は、rebase の編集画面を何もしないコマンド（`:`）で閉じる指定である。`--autosquash` が並べた順のまま、対話なしで rebase が進む。

## 5. ブランチ名

- そのリポジトリの既存のブランチ名の形に合わせる（`git branch -a` で確かめる）。リポジトリによって `feature/`・`feat/`・課題キーだけなど、形がばらばらである。
- 前例が無いときだけ `feature/<課題キー>_<要約>` にする（例: `feature/PROJ-123_slack-notification`）。要約は英小文字とハイフンで書く。
